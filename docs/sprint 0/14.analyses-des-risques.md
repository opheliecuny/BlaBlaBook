# Analyses des risques pendant le développement

## Les risques techniques

### Risque 1 - Indisponibilité ou limitation de l'API Open Library Books

| Risque      | L'API est gratuite mais peut être soumise à des limitations de débit ou des pannes temporaires. En cas d'indisponibilité, la recherche et les fiches détail ne fonctionnent plus. |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                                           |
| Impact      | Elevé                                                                                                                                                                             |
| Mesures     | Mettre en cache les résultats fréquents côté backend. Afficher un message d'erreur clair côté frontend. Implémenter un système de retry avec backoff exponentiel en cas d'échec.  |

---

### Risque 2 - Sécurité : failles d'authentification

| Risque      | Token JWT mal sécurisé (stockage en localStorage exposé au XSS), mots de passe insuffisamment protégés, routes non protégées.                                    |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                          |
| Impact      | Très élevé                                                                                                                                                       |
| Mesures     | Stocker le JWT en cookie HttpOnly. Hasher les mots de passe avec argon2. Valider toutes les entrées avec Zod. Protéger les routes sensibles avec authMiddleware. |

---

### Risque 3 - Problèmes de configuration de l'environnement de développement

| Risque      | Différences de configuration entre les machines des 4 développeurs (OS, versions Node, variables d'environnement) entraînant des bugs difficiles à reproduire. |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Elevée                                                                                                                                                         |
| Impact      | Moyen                                                                                                                                                          |
| Mesures     | Utiliser Docker pour uniformiser l'environnement. Fournir un fichier .env.example complet. Documenter la procédure d'installation dans le README.              |

---

### Risque 4 - Régression lors des merges

| Risque      | Les fusions de branches entre développeurs peuvent introduire des conflits ou casser des fonctionnalités existantes.                                                              |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Elevée                                                                                                                                                                            |
| Impact      | Moyen                                                                                                                                                                             |
| Mesures     | Travailler sur des branches dédiées par feature. Faire des Pull Requests avec code review avant tout merge sur main. Mettre en place des tests sur les fonctionnalités critiques. |

---

### Risque 5 - Déploiement défaillant

| Risque      | Les services gratuits (Render, Vercel, Supabase) ont des limites : mise en veille du backend sur Render (cold start), quotas de bande passante, indisponibilités ponctuelles. |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                                       |
| Impact      | Moyen                                                                                                                                                                         |
| Mesures     | Anticiper le cold start de Render (afficher un loader). Surveiller les quotas Supabase. Documenter une procédure de redéploiement rapide.                                     |

---

## Les risques de sécurité (Top 10 OWASP 2025)

### Risque SECURITE-1 : Contrôle d'accès défaillant (A01)

| Risque      | Un utilisateur peut accéder à des données d'autres utilisateurs en manipulant l'URL (ex : `/api/users/123` → `/api/users/456`) ou accéder à des routes admin sans autorisation.                                                                                                            |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Probabilité | Moyenne                                                                                                                                                                                                                                                                                    |
| Impact      | Très élevé                                                                                                                                                                                                                                                                                 |
| Exemple     | Modifier l'ID d'une bibliothèque dans l'URL pour voir celle d'un autre utilisateur                                                                                                                                                                                                         |
| Mesures     | - Vérifier les droits **côté serveur** sur chaque route protégée (jamais seulement en frontend) <br> - Valider que l'utilisateur possède la ressource avant toute opération <br> - Implémenter un middleware de sécurité pour valider l’appartenance et les droits d’accès aux ressources. |

---

### Risque SECURITE-2 : Injection SQL et XSS (A05)

| Risque      | Injection de code malveillant via les formulaires : SQL injection dans les recherches, XSS dans les commentaires/avis qui s'affichent ensuite pour tous les utilisateurs.                                                                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                                                                                                                                                              |
| Impact      | Très élevé                                                                                                                                                                                                                                                                                           |
| Exemples    | - Injection SQL : `' OR '1'='1` dans un champ de recherche pour contourner l'authentification <br> - XSS : `<script>alert('XSS')</script>` dans un avis de livre qui s'exécute chez tous les visiteurs <br> - Injection de commande : manipulation de paramètres pour accéder au système de fichiers |
| Mesures     | - Utiliser **Prisma ORM** avec requêtes paramétrées (jamais de concaténation SQL) <br> - Valider toutes les entrées avec **Zod** côté backend <br> - Sanitiser l'affichage avec React (échappe automatiquement) ou DOMPurify pour le HTML<br>- Echapper les caractères spéciaux dans les requêtes    |

---

### Risque SECURITE-3 : Failles d'authentification (A07)

| Risque      | Token JWT mal sécurisé (stockage en localStorage exposé au XSS), mots de passe insuffisamment protégés, absence de rate limiting permettant le credential stuffing (tentatives massives de connexion avec des identifiants volés lors de fuites de données sur d’autres sites). |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                                                                                                                                         |
| Impact      | Très élevé                                                                                                                                                                                                                                                                      |
| Exemples    | - Vol de token JWT stocké en localStorage via XSS <br> - Attaque par force brute sur `/auth/login` sans limitation <br> - Réutilisation de mots de passe faibles (123456, password) <br> - Session non invalidée après déconnexion                                              |
| Mesures     | - Stocker le JWT en **cookie HttpOnly + Secure + SameSite** <br> - Hasher les mots de passe avec **argon2** (déjà fait) <br> - Implémenter un **rate limiting** sur les routes d'authentification <br> - Invalider les tokens côté serveur                                      |

---

### Risque SECURITE-4 : Attaques CSRF (A08)

| Risque      | Un site malveillant force l'utilisateur authentifié à effectuer des actions non désirées (suppression de bibliothèque, modification de profil) en exploitant sa session active.                                                                |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Faible                                                                                                                                                                                                                                         |
| Impact      | Elevé                                                                                                                                                                                                                                          |
| Exemples    | - Un email piégé contient `<img src="https://blablabook.com/api/library/delete/123">` qui supprime la bibliothèque si l'utilisateur est connecté<br>- Formulaire malveillant qui poste sur `/api/user/update` pour changer l'email             |
| Mesures     | - Utiliser des cookies avec flag **SameSite=Strict** ou **SameSite=Lax** <br> - Implémenter un token CSRF pour les requêtes modifiant des données (POST/PUT/DELETE) <br> - Vérifier l'en-tête `Origin` ou `Referer` sur les requêtes sensibles |

---

### Risque SECURITE-5 : Défaillances cryptographiques (A04)

| Risque      | Données sensibles transmises en clair, mots de passe stockés avec un hachage faible, clés secrètes exposées dans le code ou les logs.                                                                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Faible                                                                                                                                                                                                                                                                     |
| Impact      | Très élevé                                                                                                                                                                                                                                                                 |
| Exemples    | - Transmission de données sans HTTPS (attaque man-in-the-middle) <br> - Clé secrète JWT exposée dans le repository GitHub <br> - Mots de passe hachés avec MD5 ou SHA1 (faibles et cassables) <br> - Logs contenant des tokens ou mots de passe en clair                   |
| Mesures     | - Forcer **HTTPS** partout (frontend et backend) <br> - Utiliser **argon2** pour les mots de passe (déjà fait) <br> - Stocker les secrets dans des variables d'environnement (.env) **jamais committées** <br> - Ne jamais logger de données sensibles (tokens, passwords) |

---

## Les risques organisationnels

### Risque 6 - Mauvaise répartition des tâches

| Risque      | Un développeur se retrouve bloqué ou surchargé, créant un déséquilibre dans l'avancement du projet.                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                                    |
| Impact      | Elevé                                                                                                                                                                      |
| Mesures     | Utiliser le Kanban GitHub pour visualiser la charge de chacun. Faire un point d'équipe quotidien (stand-up). Réattribuer les tâches si un blocage dure plus d'une journée. |

---

### Risque 7 - Sous-estimation de la charge de travail

| Risque      | Le projet est ambitieux pour 1 mois à niveau junior. Certaines fonctionnalités peuvent prendre plus de temps que prévu et mettre le MVP en péril.                                          |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Probabilité | Elevée                                                                                                                                                                                     |
| Impact      | Elevé                                                                                                                                                                                      |
| Mesures     | Prioriser strictement le MVP. Renoncer rapidement aux fonctionnalités non essentielles si le planning se resserre. Ne pas commencer les évolutions (v2, v3) avant que le MVP soit réalisé. |

--

### Risque 8 - Conflits Git non gérés

| Risque      | Sans discipline de versionning, les conflits s'accumulent et font perdre du temps à toute l'équipe.                                                        |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Probabilité | Moyenne                                                                                                                                                    |
| Impact      | Moyen                                                                                                                                                      |
| Mesures     | Définir des conventions de nommage de branches (feature/, fix/, chore/). Faire des commits atomiques et réguliers. Ne jamais pousser directement sur main. |
