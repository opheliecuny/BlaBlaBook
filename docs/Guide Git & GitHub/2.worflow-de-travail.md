# Workflow de travail sur une branche

Ce workflow est à suivre pour chaque nouvelle tâche, sans gestionnaire d’issues.

## 1.1. Se mettre à jour depuis `main`

```bash
git checkout main
git pull origin main
```

### 1.2. Créer une nouvelle branche

Choisir un type et une description claire :

```bash
git checkout -b feature/user-login-page

# ou

git checkout -b fix/header-overflow-mobile
```

### 1.3. Développer et faire des commits réguliers

Cycle simple :

```bash
# après un ensemble de changements cohérents
git add .
git commit -m "feat(auth): add login form validation"
```

## Bonnes pratiques

- Un commit = une idée cohérente (pas tout le sprint)
- Commits en anglais, description courte et claire
- Eviter les commits vagues du type `misc changes`

### 1.4. Poussez la branche sur GitHub

```bash
git push -u origin feature/user-login-page
```

---

## 2. Créer une Pull Request vers `main`

### 2.1 Depuis l'interface GitHub

1. Aller sur la page du dépôt GitHub.

2. Si GitHub propose **"Compare & pull request"** pour la branche, cliquer dessus.
    - Sinon : onglet **Pull requests** → bouton **New pull request**

3. Vérifier que :
    - `base` = `main` (branche de destination).
    - `compare` = la branche (`feature/user-login-page`).

4. Vérifier l’onglet **Files changed** pour s’assurer que seuls les bons fichiers sont modifiés.

### 2.2 Titre de la Pull Request

Format recommandé :

```plaintext
<type>: <résumé court en français>
```

**Exemples :**

- `feat: ajouter la page de connexion utilisateur`
- `fix: corriger l’overflow sur le header mobile`
- `refactor: simplifier le service utilisateur`

### 2.3 Description de la Pull Request (template)

La PR doit utiliser le template défini dans `.github/pull_request_template.md` (voir section 4).

Le but est de décrire clairement :

- L’objectif de la PR
- Les changements principaux
- Comment tester
- Les remarques / limites éventuelles

## 3. Validation, CI et fusion dans `main`

### 3.1 Revue du code entre dev

Organisation conseillée pour l’équipe :

- Au moins **1 reviewer** différent de l’auteur de la PR
- Le reviewer vérifie :
  - Que le titre de la PR est clair
  - Que les messages de commits respectent la convention
  - Que la taille de la PR est raisonnable
  - Que le code est compréhensible et cohérent avec le reste du projet

### 3.2 Intégration continue (CI) sur GitHub

Ajouter une CI via GitHub Actions

Une fois configurée, on pourra :

- Activer l’option « Require status checks to pass before merging » sur la branche main
- Optionnel : exiger que la branche soit à jour avec `main` avant le merge (« Require branches to be up to date before merging »)

**Conséquences :**

- Une PR ne pourra être fusionnée que si tous les checks CI sont verts
- Cela évite de casser main à cause d’un test qui échoue

### 3.3 Corriger après review

- Les remarques sont faites dans la PR
- L’auteur applique les corrections sur la même branche puis pousse un nouveau commit
- La PR se met automatiquement à jour

### 3.4 Fusion dans `main`

Stratégie recommandée : Squash and merge

- Cela transforme tous les commits de la branche en un seul commit propre sur `main`
- On peut alors écrire un message de commit conforme à Conventional Commits

Exemple de message de squash pour le merge :

```plaintext
feat(auth): add user login page
```

Après merge :

- Supprimer la branche distante via le bouton "Delete branch"
- Nettoyer localement :

```bash
git checkout main
git pull origin main
git branch -d feature/user-login-page
```

## 4. Template de Pull Request (`.github/pull_request_template.md`)

Créer le fichier suivant dans le dépôt :
> `.github/pull_request_template.md`

Contenu à copier-coller tel quel :

```plaintext
## Objet

Décrire en 1 ou 2 phrases l'objectif principal de cette PR.

## Changements

Lister les principaux changements apportés :

- ...
- ...
- ...

## Comment tester

Explique comment un autre développeur peut tester la PR :

1. Etape 1
2. Etape 2
3. Résultat attendu

## Checklist

- [ ] Le titre de la PR est clair
- [ ] Les messages de commits respectent la convention (feat, fix, docs, refactor, test)
- [ ] Les tests passent en local
- [ ] Les checks CI sont verts (si configurés)
- [ ] La PR ne contient pas de changements sans rapport avec le sujet

## Remarques

Ajouter ici les limitations connues, points à surveiller ou TODO ultérieurs.
```

---

## 5. Résumé des règles d'équipe

- Jamais de commit directement sur `main`
- Une **tâche** = une **branche** = une **Pull Request**
- Branches : `feature/…`, `fix/…`, `docs/…`, `refactor/…`, `test/…`
- Commits en **anglais** avec les types : *feat*, *fix*, *docs*, *refactor*, *test*
- Toujours mettre à jour `main` et créer une nouvelle branche avant de commencer une tâche
- Utiliser la **revue de code** + CI (quand elle sera en place) avant de merger
