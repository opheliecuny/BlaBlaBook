# Mode opératoire : Mise en place des tests automatiques via GitHub Actions

Ce guide documente la configuration de l'**intégration continue (CI)** avec GitHub Actions pour BlaBlaBook.

> **✅ Statut** : CI/CD implémenté et fonctionnel (24/03/2026)

---

## Vue d'ensemble

Le workflow CI/CD est configuré dans [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) et s'exécute automatiquement à chaque **push** et **Pull Request** vers `main`.

### Architecture du workflow

Le workflow est organisé en **5 jobs indépendants** :

| Job              | Description                                       | Dépendances   |
| ---------------- | ------------------------------------------------- | ------------- |
| `lint-backend`   | Vérification ESLint du backend                    | Aucune        |
| `test-backend`   | 73 tests Vitest + couverture (PostgreSQL service) | Aucune        |
| `build-backend`  | Compilation TypeScript                            | lint + test   |
| `lint-frontend`  | Vérification ESLint du frontend                   | Aucune        |
| `build-frontend` | Build Next.js                                     | lint-frontend |

### Caractéristiques clés

- ✅ **Node.js 22** sur tous les jobs
- ✅ **Cache npm** pour accélérer les installations
- ✅ **Service PostgreSQL 17** avec health checks pour tests d'intégration
- ✅ **73 tests Vitest** (33 unitaires + 40 intégration)
- ✅ **91% de couverture** (statements)
- ✅ **Prisma migrations** automatiques avant les tests
- ✅ **Upload Codecov** optionnel pour visualiser la couverture

## Configuration détaillée

### 1. Déclencheurs

```yaml
on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main
```

Le workflow se déclenche sur :

- Tout push direct vers `main`
- Toute Pull Request vers `main`

### 2. Job `lint-backend`

Vérifie la qualité du code backend avec ESLint.

**Étapes :**

1. Checkout du code
2. Setup Node.js 22 avec cache npm
3. Installation des dépendances (`npm ci`)
4. Génération du client Prisma (nécessaire pour le typage)
5. Exécution du lint (`npm run lint`)

### 3. Job `test-backend` ⭐ (Critical)

Le job le plus important : exécute tous les tests backend avec une base PostgreSQL réelle.

**Service PostgreSQL :**

```yaml
services:
  postgres:
    image: postgres:17
    env:
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
      POSTGRES_DB: blablabook_test
    ports:
      - 5432:5432
    options: >-
      --health-cmd pg_isready
      --health-interval 10s
      --health-timeout 5s
      --health-retries 5
```

**Variables d'environnement :**

```yaml
env:
  DATABASE_URL: postgresql://test:test@localhost:5432/blablabook_test
  JWT_SECRET: ci-secret-key-minimum-32-characters-long-for-testing
  JWT_EXPIRES_IN: 1h
  PORT: 3000
  ALLOWED_ORIGINS: "*"
  NODE_ENV: test
```

**Étapes :**

1. Checkout du code
2. Setup Node.js 22 avec cache npm
3. Installation des dépendances
4. Génération du client Prisma
5. Application des migrations (`npx prisma migrate deploy`)
6. Exécution des tests (`npm test`)
7. Génération du rapport de couverture (`npm run test:coverage`)
8. Upload optionnel vers Codecov

**Résultats attendus :**

- ✅ 73 tests passent (33 unitaires + 40 intégration)
- ✅ Couverture : 91% statements, 87% branches, 100% functions, 93% lines

### 4. Job `build-backend`

Compile le TypeScript vers JavaScript pour vérifier qu'il n'y a pas d'erreurs de compilation.

**Dépendances :** `needs: [lint-backend, test-backend]`

Ce job ne s'exécute que si le lint et les tests sont verts.

### 5. Job `lint-frontend`

Vérifie la qualité du code frontend avec ESLint Next.js.

### 6. Job `build-frontend`

Compile l'application Next.js pour vérifier qu'il n'y a pas d'erreurs de build.

**Dépendances :** `needs: [lint-frontend]`

**Variable d'environnement :**

```yaml
env:
  NEXT_PUBLIC_API_URL: http://localhost:3000
```

## Configuration locale requise

### Backend (`blablabook/backend/package.json`)

```json
{
  "scripts": {
    "test": "vitest run",
    "test:unit": "vitest run --testPathPattern=unit",
    "test:spec": "vitest run --testPathPattern=spec",
    "test:coverage": "vitest run --coverage",
    "lint": "eslint src/**/*.ts",
    "build": "tsc"
  }
}
```

### Frontend (`blablabook/frontend/package.json`)

```json
{
  "scripts": {
    "lint": "next lint",
    "build": "next build"
  }
}
```

### Configuration Vitest (`blablabook/backend/vitest.config.ts`)

```typescript
export default defineConfig({
  test: {
    globals: true,
    environment: "node",
    fileParallelism: false, // Important pour éviter les conflits BDD
    include: ["tests/**/*.{test,spec}.{ts,tsx}", "src/**/*.test.ts"],
    exclude: ["node_modules", "dist", "prisma/migrations"],
    coverage: {
      provider: "v8",
      reporter: ["text", "lcov", "html"],
      thresholds: {
        lines: 70,
        functions: 75,
        branches: 45,
        statements: 70,
      },
    },
    setupFiles: ["./tests/setup.ts"],
  },
});
```

## Protections de branche (à configurer manuellement)

### Accéder aux paramètres

1. Aller sur GitHub → **Settings**
2. Menu de gauche : **Branches**
3. Cliquer sur **Add rule**

### Configuration recommandée pour `main`

| Paramètre                                     | Valeur                                                                             |
| --------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Branch name pattern**                       | `main`                                                                             |
| **Require a pull request before merging**     | ✅ Coché                                                                            |
| **Require approvals**                         | 1 (au moins un reviewer)                                                           |
| **Require status checks to pass**             | ✅ Coché                                                                            |
| **Status checks required**                    | `lint-backend`, `test-backend`, `build-backend`, `lint-frontend`, `build-frontend` |
| **Require branches to be up to date**         | ✅ Coché                                                                            |
| **Do not allow bypassing the above settings** | ✅ Coché                                                                            |

## Workflow de développement avec CI

### 1. Créer une branche de feature

```bash
git checkout main
git pull origin main
git checkout -b feature/ma-nouvelle-fonctionnalite
```

### 2. Développer et tester localement

```bash
# Backend
cd blablabook/backend
npm run lint
npm test
npm run test:coverage

# Frontend
cd blablabook/frontend
npm run lint
npm run build
```

### 3. Commit et push

```bash
git add .
git commit -m "feat: ajouter ma nouvelle fonctionnalité"
git push -u origin feature/ma-nouvelle-fonctionnalite
```

> ⚠️ **Note importante** : Cette fonctionnalité nécessite des permissions administrateur sur le dépôt.
> Sur les dépôts d'organisation (écoles, entreprises), cette option peut être désactivée par l'administrateur de l'organisation.
> Si l'option "Branches" n'apparaît pas dans les Settings ou si vous ne pouvez pas créer de règles, contactez l'administrateur de votre organisation.
> **Le workflow CI fonctionnera quand même**, mais la fusion ne sera pas bloquée automatiquement en cas d'échec des tests.

### 5.1. Accéder aux paramètres du dépôt

1. Aller sur GitHub
2. Créer une PR depuis `feature/ma-nouvelle-fonctionnalite` vers `main`
3. **Les 5 jobs CI se lancent automatiquement**
4. Attendre que tous les checks soient verts ✅

### 5. Code Review et Merge

1. Un membre de l'équipe review le code
2. Si des modifications sont demandées :

   ```bash
   # Faire les modifications localement
   git add .
   git commit -m "fix: corriger suite à la review"
   git push
   # Les checks CI se relancent automatiquement
   ```

3. Une fois les checks verts et la review approuvée, **fusionner la PR**

## Déboguer les échecs CI

### Accéder aux logs

1. Aller sur l'onglet **Actions** du dépôt GitHub
2. Cliquer sur le workflow qui a échoué
3. Cliquer sur le job en erreur (ex: `test-backend`)
4. Développer les étapes pour voir les logs détaillés

### Erreurs courantes

#### ❌ `lint-backend` échoue

**Cause :** Erreurs ESLint dans le code

**Solution :**

```bash
cd blablabook/backend
npm run lint
# Corriger les erreurs signalées
```

#### ❌ `test-backend` échoue

**Cause :** Tests qui échouent ou couverture insuffisante

**Solution :**

```bash
cd blablabook/backend
npm test
# Corriger les tests qui échouent

npm run test:coverage
# Vérifier la couverture
```

#### ❌ `build-backend` échoue

**Cause :** Erreurs de compilation TypeScript

**Solution :**

```bash
cd blablabook/backend
npm run build
# Corriger les erreurs TypeScript
```

#### ❌ `build-frontend` échoue

**Cause :** Erreurs Next.js (imports manquants, erreurs TypeScript, etc.)

**Solution :**

```bash
cd blablabook/frontend
npm run build
# Corriger les erreurs signalées
```

## Tests locaux avant push

Pour éviter les échecs CI, toujours tester localement avant de push :

```bash
# Script de vérification complète (à la racine du projet)
cd blablabook/backend && npm run lint && npm test && npm run build && cd ../..
cd blablabook/frontend && npm run lint && npm run build && cd ../..
```

Vous pouvez créer un script npm à la racine pour automatiser :

```json
{
  "scripts": {
    "ci:check": "cd blablabook/backend && npm run lint && npm test && npm run build && cd ../.. && cd blablabook/frontend && npm run lint && npm run build"
  }
}
```

Puis :

```bash
npm run ci:check
```

## Notes importantes

- **`npm ci`** est utilisé au lieu de `npm install` car il est plus rapide et reproductible
- Les workflows sont visibles dans l'onglet **Actions** du dépôt GitHub
- Les jobs s'exécutent en **parallèle** (sauf build qui attend lint + test)
- Le service PostgreSQL est automatiquement démarré et arrêté pour chaque run
- Les logs complets sont disponibles pendant 90 jours sur GitHub
