# Guide Git et GitHub de l'équipe

## 1. Convention de nommage des branches

**Format :**

```plaintext
<type>/<description-kebab-case>
```

### Types de branches proposés

- `feature/` pour une nouvelle fonctionnalité
- `fix/` pour une correction de bug
- `docs/` pour la documentation uniquement
- `refactor/` pour une refactorisation sans changement fonctionnel
- `test/` pour ajouter ou modifier des tests

### Règles pour la description

- Tout en minuscules
- Mots séparés par des tirets `-`
- 3 à 6 mots, clairs et concrets

### Exemples

- `feature/user-login-page`
- `fix/header-overflow-mobile`
- `docs/api-authentication-guide`
- `refactor/user-service-split`
- `test/authentication-flows`

## 2. Convention de commit

Chaque message de commit doit suivre la structure :

```plaintext
<type>(<scope>): <short english description>
```

- type est obligatoire
- scope est optionnel (un mot décrivant la zone de code)
- short english description est en anglais, au présent, concise (~60 caractères max)

### Types autorisés dans le projet

- **feat** : ajout d’une nouvelle fonctionnalité
- **fix** : correction de bug
- **docs** : changement de documentation uniquement
- **refactor** : modification de code qui n’ajoute pas de fonctionnalité et ne corrige pas de bug
- **test** : ajout ou modification de tests uniquement

### Exemples de bons commits

- `feat(auth)` : add login page
- `feat(api)` : expose user profile endpoint
- `fix(header)` : keep menu visible on scroll
- `docs(readme)` : add setup instructions
- `refactor(user-service)` : split repository layer
- `test(auth)` : add login failure cases
