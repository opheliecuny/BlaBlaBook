# Mode opératoire : Synchronisation des branches vers `main`

Ce guide détaille les étapes pour synchroniser et fusionner les modifications de plusieurs développeurs travaillant sur des branches distinctes vers la branche `main`.

---

## Contexte

Vous avez plusieurs développeurs qui ont travaillé en parallèle sur des branches distinctes et vous souhaitez maintenant synchroniser toutes ces modifications dans la branche `main`.

---

## Prérequis

- Chaque développeur a travaillé sur une branche dédiée
- Les branches ont été poussées sur GitHub
- Accès au dépôt GitHub

---

## Vue d'ensemble du processus

```plaintext
┌─────────────────────┐
│ Branches dev        │
│ - feature/login     │──┐
│ - feature/search    │──┤
│ - docs/database     │──┼──> Fusion vers main
│ - fix/header        │──┤
└─────────────────────┘──┘
         ↓
┌─────────────────────┐
│ Branche main        │
│ (mise à jour)       │
└─────────────────────┘
```

---

## Etape 1 : Inventaire des branches à synchroniser

### 1.1. Lister toutes les branches distantes

```bash
git fetch origin
git branch -r
```

**Résultat attendu :**

```plaintext
origin/main
origin/feature/user-login
origin/feature/book-search
origin/docs/database-schema
origin/fix/header-overflow
```

### 1.2. Identifier les branches à fusionner

Créer une liste des branches à synchroniser avec leurs auteurs :

| Branche                | Développeur | Fonctionnalité      | Priorité |
| ---------------------- | ----------- | ------------------- | -------- |
| `docs/database-schema` | Dev A       | Documentation BDD   | 1 (base) |
| `feature/user-auth`    | Dev B       | Authentification    | 2        |
| `feature/book-search`  | Dev C       | Recherche de livres | 3        |
| `fix/header-overflow`  | Dev D       | Correction header   | 4        |

**Conseil :** Fusionner dans l'ordre logique (documentation → features → fixes)

---

## Etape 2 : Préparer l'environnement local

### 2.1. Se positionner sur `main` et mettre à jour

```bash
git checkout main
git pull origin main
```

### 2.2. Vérifier l'état de `main`

```bash
git status
git log --oneline -5
```

**Résultat attendu :** `main` doit être propre (aucune modification en cours)

---

## Etape 3 : Synchroniser chaque branche (méthode recommandée : Pull Request)

### Méthode A : Via Pull Request sur GitHub (RECOMMANDE)

#### 3.1. Créer une Pull Request pour chaque branche

Pour chaque branche à fusionner :

1. **Aller sur GitHub** → onglet **Pull requests**
2. Cliquer sur **New pull request**
3. Configurer :
   - **base :** `main`
   - **compare :** la branche à fusionner (ex : `feature/user-login`)
4. Vérifier les **Files changed** pour confirmer les modifications
5. Remplir le titre et la description :

**Exemple de titre :**

```plaintext
feat: ajouter la page de connexion utilisateur
```

**Exemple de description :**

```markdown
## Objet

Ajouter la page de connexion utilisateur avec authentification JWT.

## Changements

- Création de la page `/login`
- Intégration de l'API d'authentification
- Validation des formulaires

## Comment tester

1. Lancer le frontend : `npm run dev`
2. Accéder à `/login`
3. Se connecter avec des identifiants valides
4. Vérifier la redirection vers le dashboard

## Checklist

- [x] Le titre de la PR est clair
- [x] Les messages de commits respectent la convention
- [x] Les tests passent en local
- [x] La PR ne contient pas de changements sans rapport
```

6. Cliquer sur **Create pull request**

#### 3.2. Demander une revue de code

1. Assigner un **reviewer** (un autre développeur)
2. Le reviewer vérifie le code et commente si nécessaire
3. L'auteur corrige les remarques si besoin
4. Le reviewer **approuve** la PR

#### 3.3. Vérifier les checks CI (si configurés)

Si GitHub Actions est configuré, attendre que tous les tests soient **verts** ✅

#### 3.4. Fusionner la Pull Request

1. Vérifier que la PR est **approuvée** et que les **checks CI sont verts**
2. Cliquer sur **Squash and merge** (recommandé)
3. Modifier le message de commit si nécessaire :

```plaintext
feat(auth): add user login page

- Create login page with form validation
- Integrate JWT authentication
- Add redirect to dashboard after login
```

4. Cliquer sur **Confirm squash and merge**
5. Supprimer la branche distante en cliquant sur **Delete branch**

#### 3.5. Mettre à jour `main` en local

```bash
git checkout main
git pull origin main
```

#### 3.6. Nettoyer la branche locale (si elle existe)

```bash
git branch -d feature/user-login
```

---

### Méthode B : Fusion locale (alternative, moins recommandée)

Si vous préférez fusionner localement sans passer par GitHub :

#### 3.1. Récupérer la branche distante

```bash
git fetch origin
git checkout feature/user-login
git pull origin feature/user-login
```

#### 3.2. Revenir sur `main` et fusionner

```bash
git checkout main
git merge feature/user-login --no-ff
```

**Explication :**

- `--no-ff` : Force la création d'un commit de merge (traçabilité)

#### 3.3. Résoudre les conflits (si nécessaire)

Si Git signale des conflits :

```plaintext
CONFLICT (content): Merge conflict in src/App.js
```

1. Ouvrir les fichiers en conflit
2. Rechercher les marqueurs `<<<<<<<`, `=======`, `>>>>>>>`
3. Choisir la version à conserver ou fusionner manuellement
4. Supprimer les marqueurs
5. Ajouter et commiter :

```bash
git add .
git commit -m "merge: resolve conflicts from feature/user-login"
```

#### 3.4. Pousser sur `main`

```bash
git push origin main
```

#### 3.5. Supprimer la branche locale et distante

```bash
git branch -d feature/user-login
git push origin --delete feature/user-login
```

---

## Etape 4 : Répéter pour toutes les branches

Pour chaque branche restante, répéter **l'Etape 3** dans l'ordre de priorité défini.

### Ordre recommandé

1. **Documentation** (`docs/database-schema`)
2. **Features fondamentales** (`feature/user-auth`)
3. **Features secondaires** (`feature/book-search`)
4. **Corrections** (`fix/header-overflow`)

---

## Etape 5 : Vérification finale

### 5.1. Vérifier que `main` contient toutes les modifications

```bash
git checkout main
git pull origin main
git log --oneline --graph -10
```

**Résultat attendu :** L'historique doit montrer tous les merges

### 5.2. Lancer les tests

```bash
# Backend
cd backend
npm install
npm test

# Frontend
cd ../frontend
npm install
npm test
```

### 5.3. Lancer l'application en local

```bash
# Terminal 1 : Backend
cd backend
npm run dev

# Terminal 2 : Frontend
cd frontend
npm run dev
```

Vérifier que tout fonctionne correctement.

---

## Etape 6 : Nettoyage final

### 6.1. Lister les branches obsolètes

```bash
git fetch --prune
git branch -a
```

### 6.2. Supprimer les branches locales fusionnées

```bash
git branch --merged main | grep -v "^\*\|main" | xargs git branch -d
```

**Explication :**

- Liste toutes les branches fusionnées dans `main`
- Exclut `main` elle-même
- Supprime toutes les branches locales obsolètes

### 6.3. Vérifier les branches distantes restantes

```bash
git branch -r
```

Si des branches distantes existent encore, les supprimer manuellement :

```bash
git push origin --delete feature/old-branch
```

## Gestion des conflits : Guide détaillé

### Scénario : Deux branches modifient le même fichier

**Exemple :**

- `feature/user-login` modifie `src/components/Header.jsx`
- `feature/book-search` modifie aussi `src/components/Header.jsx`

### 1. Identifier le conflit

Lors du merge, Git affiche :

```plaintext
Auto-merging src/components/Header.jsx
CONFLICT (content): Merge conflict in src/components/Header.jsx
Automatic merge failed; fix conflicts and then commit the result.
```

### 2. Ouvrir le fichier en conflit

```bash
code src/components/Header.jsx
```

### 3. Comprendre les marqueurs de conflit

```jsx
export default function Header() {
  return (
    <header>
<<<<<<< HEAD
      <nav>
        <a href="/login">Connexion</a>
      </nav>
=======
      <nav>
        <a href="/search">Rechercher</a>
      </nav>
>>>>>>> feature/book-search
    </header>
  );
}
```

**Explication :**

- `<<<<<<< HEAD` : Code de la branche actuelle (`main`)
- `=======` : Séparateur
- `>>>>>>> feature/book-search` : Code de la branche à fusionner

### 4. Résoudre le conflit

**Option 1 : Garder les deux modifications**

```jsx
export default function Header() {
  return (
    <header>
      <nav>
        <a href="/login">Connexion</a>
        <a href="/search">Rechercher</a>
      </nav>
    </header>
  );
}
```

**Option 2 : Garder une seule version**

Supprimer les marqueurs et garder uniquement le code souhaité.

### 5. Marquer le conflit comme résolu

```bash
git add src/components/Header.jsx
git commit -m "merge: resolve conflicts in Header component"
```

### 6. Pousser les modifications

```bash
git push origin main
```

## Checklist finale

Avant de considérer la synchronisation comme terminée :

- [ ] Toutes les branches prioritaires ont été fusionnées dans `main`
- [ ] Aucun conflit non résolu
- [ ] Les tests passent sur `main`
- [ ] L'application fonctionne en local
- [ ] Les branches obsolètes ont été supprimées (locales et distantes)
- [ ] L'équipe a été informée de la mise à jour de `main`

---

## Bonnes pratiques

1. **Fusionner dans l'ordre logique** : documentation → features → fixes
2. **Toujours utiliser les Pull Requests** pour tracer les modifications
3. **Demander une revue de code** avant chaque fusion
4. **Tester après chaque fusion** pour détecter les régressions rapidement
5. **Communiquer avec l'équipe** avant et après les fusions importantes
6. **Utiliser `git log --graph`** pour visualiser l'historique
